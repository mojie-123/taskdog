## 问题一：Instanceable 机制详解

### 先从为什么要有 Instanceable 说起

Isaac Lab 经常需要并行运行几百个仿真环境（例如强化学习中的 4096 个 env）。如果每个环境都单独存一份机器人的几何数据（顶点坐标、法线、面索引……），M20_Piper 的 base.usd 就有 30MB，4096 个环境就是 4096 × 30MB ≈ **120GB** 的内存——完全不可行。

`make_instanceable=True` 就是为了解决这个问题。

---

### USD Instanceable 的核心概念

USD 的实例化分三个角色：

```
┌──────────────────────────────────────────────────────────┐
│  Prototype（原型）                                         │
│  ─ 几何数据只在这里存一份                                   │
│  ─ 路径例如：/colliders/link7/link7（在 base.usd 里）       │
│  ─ 不直接出现在仿真场景树里，是「幕后」的数据仓库              │
└────────────────────────┬─────────────────────────────────┘
                         │ 共享（零拷贝）
          ┌──────────────┼───────────────┐
          ▼              ▼               ▼
   Instance 0      Instance 1      Instance 2  ...
  /World/Env_0/   /World/Env_1/   /World/Env_2/
  Robot/link7/    Robot/link7/    Robot/link7/
  collisions/     collisions/     collisions/
  link7           link7           link7
  （Instance Proxy） （Instance Proxy） （Instance Proxy）
```

每个 `Instance Proxy`（实例代理）的行为：
- **可以读**：可以查询几何数据（顶点、法线等），因为代理转发到 Prototype
- **不可以写**：不能在实例代理上直接修改/添加属性，因为它背后没有独立的数据存储，只是一个「指针」指向 Prototype

---

### 为什么 `stage.GetPrimAtPath()` 不能修改 link7/link8？

**关键**：当 `make_instanceable=True` 时，UrdfConverter 在生成 USD 时把所有 link 的几何 prim 放在 **Prototype** 里（路径是 `/colliders/link7/link7`，在 `M20_Piper_base.usd` 内）。

在实际仿真场景中，`/World/Env_0/Robot/link7/collisions/link7` 是一个 **Instance Proxy**，它指向 Prototype，本身没有数据。

如果你用 `stage.GetPrimAtPath("/World/Env_0/Robot/link7/collisions/link7")` 取到这个 prim，然后尝试在它上面加属性：

```python
prim = stage.GetPrimAtPath("/World/Env_0/Robot/link7/collisions/link7")
prim.GetAttribute("physics:approximation").Set("convexDecomposition")
# ↑ 这行在 Instance Proxy 上操作，USD 会报错或静默忽略
```

这相当于你找到了一面镜子里的影像，然后试图在影像上写字——影像本身没有纸，字是写不上去的。必须找到「真正的那面墙」（Prototype）才能写。

**正确的做法**（patch 脚本的做法）：

不走 stage API，而是直接操作 **SdfLayer**（可以理解为 USD 文件的底层数据层），在 `/colliders/link7/link7` 这个 Prototype 路径上直接写 Spec（规格）：

```python
# 打开 base.usd 的 layer（而不是打开场景 stage）
layer = Sdf.Layer.FindOrOpen(str(base_usd))

# 找到 Prototype 的 SdfPrimSpec（直接对原始数据操作）
prim_spec = layer.GetPrimAtPath("/colliders/link7/link7")

# 修改 specifier 为 Def，type 为 Mesh（这才真正写入了 Prototype）
prim_spec.specifier = Sdf.SpecifierDef
prim_spec.typeName = "Mesh"
```

这相当于直接改了「原版画」，所有镜子里的影像（所有 Instance Proxy，即所有 env 里的 link7）都自动跟着改变。

---

### 直观总结

| | Prototype（`/colliders/link7/link7`） | Instance Proxy（`/World/Env_N/Robot/link7/collisions/link7`） |
|---|---|---|
| 存储位置 | `M20_Piper_base.usd` 文件内 | 仅是一个「指针」，无自身存储 |
| 能否直接读 | ✅ | ✅（转发到 Prototype）|
| 能否直接写 | ✅（通过 SdfLayer） | ❌（写不进去）|
| 有几份数据 | 1 份 | N 份（N = env 数量），但共享同 1 份数据 |
| API | `Sdf.Layer + SdfPrimSpec` | `stage.GetPrimAtPath()` |

## 问题二：Step 1 的三个子问题

### (A) 为什么要把 mesh 路径从相对路径改为绝对路径？

原始 URDF 里的 mesh 路径是这样写的：

```xml
<mesh filename="./meshes/base_link.STL"/>
```

这个 `./` 是**相对于 URDF 文件本身所在目录**的路径。原始 URDF 在：
```
deps/deep_robotics_model/M20_Piper/urdf/M20_Piper.urdf
```
所以 `./meshes/base_link.STL` 解析为：
```
deps/deep_robotics_model/M20_Piper/urdf/meshes/base_link.STL
```

**build 脚本把 URDF 复制到了另一个目录**（`custom_envs/assets/m20_piper_single/M20_Piper_lightweight.urdf`），这时候 `./meshes/` 就不存在了，相对路径失效。

Isaac Sim 的 UrdfConverter 读取 URDF 时，是以**URDF 文件所在目录**为基准解析相对路径的。如果 URDF 搬了家但 mesh 没搬，就必须用绝对路径告诉 UrdfConverter 去哪里找。

build 脚本的处理：
```python
for mesh in root.findall(".//mesh"):
    mesh_path = Path(mesh.attrib["filename"])
    if not mesh_path.is_absolute():
        resolved = (SOURCE_URDF.parent / mesh_path).resolve()
        # SOURCE_URDF.parent = deps/.../urdf/
        # resolved = deps/.../urdf/meshes/base_link.STL（绝对路径）
        mesh.attrib["filename"] = str(resolved)
```

这样 UrdfConverter 不管在哪个目录下运行，都能找到正确的 STL 文件。

### (B) PIPER_COLLIDERS 字典是什么？

原始 URDF 里，Piper 机械臂的每个关节（link1~link6、gripper_base 等）都用**STL mesh**作为碰撞几何：

```xml
<link name="link2">
  <collision>
    <geometry>
      <mesh filename="./meshes/link2.STL"/>  <!-- 高精度 STL，几千个三角面 -->
    </geometry>
  </collision>
</link>
```

这带来两个问题：
1. **UrdfConverter 对 STL mesh collision 支持不完整**（这正是 link7/link8 问题的根源）
2. **PhysX 对复杂 mesh 做 convex hull/decomposition 很慢**，启动时间长，内存占用高

`PIPER_COLLIDERS` 字典定义了每个 Piper 关节的**简化碰撞体**：

```python
PIPER_COLLIDERS = {
    "arm_base_link": ("cylinder", "0 0 0.045", "0 0 0", {"radius": "0.075", "length": "0.09"}),
    "link1":   ("cylinder", "0 0 0",     "0 0 0", {"radius": "0.065", "length": "0.10"}),
    "link2":   ("box",      "0.14 0 0",  "0 0 0", {"size": "0.28 0.07 0.07"}),
    "link3":   ("box",      "0 -0.125 0","0 0 0", {"size": "0.07 0.25 0.07"}),
    "link4":   ("cylinder", "0 0 0",     "0 0 0", {"radius": "0.060", "length": "0.10"}),
    "link5":   ("box",      "0 -0.050 0","0 0 0", {"size": "0.07 0.11 0.07"}),
    "link6":   ("cylinder", "0 0 0",     "0 0 0", {"radius": "0.045", "length": "0.05"}),
    "gripper_base": ("box", "0 0 0.032", "0 0 0", {"size": "0.075 0.075 0.064"}),
    # link7/link8 故意不在这里 → 保留原始 STL mesh collision
}
```

含义：把原来高精度 STL 碰撞体替换为对应的几何原语：
- `link2`（大臂）→ 一个 `28cm × 7cm × 7cm` 的 box
- `link3`（小臂）→ 一个 `7cm × 25cm × 7cm` 的 box  
- `arm_base_link`（臂基座）→ 一个半径 7.5cm、高 9cm 的 cylinder

**为什么 link7/link8 不在字典里**？注释已经说明：夹爪手指需要精确的接触检测（抓香蕉），所以故意保留原始 STL mesh 碰撞。但 UrdfConverter 处理不了 mesh collision，这才有了 patch 脚本来补救。

### (C) Step 3："从空 Xform → Mesh，复制顶点数据" 是什么意思？

**背景**：UrdfConverter 在转换时遇到 link7/link8 的 `<collision><geometry><mesh>` 标签，它不知道怎么处理（bug 或限制），于是产生了一个**空的 Xform prim**（Xform 是 USD 里纯粹的坐标变换节点，没有任何几何数据，等同于一个空文件夹）：

```
转换后 base.usd 里的状态：
/colliders/link7/link7   ← 类型是 Xform，里面什么都没有
/visuals/link7/link7/node_STL_BINARY_/mesh  ← 类型是 Mesh，有完整的 6258 个顶点
```

**视觉（visuals）和碰撞（colliders）是分开存储的**。视觉部分的 mesh 被正常转换了（因为 UrdfConverter 支持 visual mesh），碰撞部分的 mesh 没有被转换（只生成了空 Xform）。

patch 脚本要做的事，用人话说就是：

> 把视觉那边的 mesh 数据，拷贝一份到碰撞这边，并且把碰撞 prim 的类型从「空文件夹（Xform）」改成「真正有几何体的（Mesh）」。

具体步骤：
```
① 打开 base.usd
② 读取 /visuals/link7/link7/node_STL_BINARY_/mesh 的属性：
   - points（6258 个顶点坐标）
   - faceVertexCounts（每个面的顶点数）
   - faceVertexIndices（顶点索引）
   - normals（法线）
   - extent（包围盒）
③ 找到 /colliders/link7/link7 这个空 Xform prim
④ 把它的类型改成 Mesh
⑤ 把 ② 读出的所有属性写入到 ③ 这个 prim
⑥ 保存
```

然后对 physics.usd 做配套修改：
```
① 在 /colliders/link7/link7 上添加 PhysicsCollisionAPI
   → 告诉 PhysX "这个 prim 是碰撞体"
② 设置 physics:approximation = convexDecomposition
   → 告诉 PhysX 用 convex decomposition 算法处理这个 mesh
```

做完这两步，PhysX 才能「看见」手指，才能产生接触力，才能抓住香蕉。

## 问题四：`piper/` 目录如何被项目使用

有**两条独立的使用链路**，分别服务不同目的：

### 链路 A：通过 `piper_arm.py`（历史遗留，现在不用于主任务）

```
piper/piper.usd
  └─ 被 piper_arm.py 的 PIPER_ARM_CFG 引用
       └─ 被 piper_env_cfg.py 的 PiperEnvCfg 引用
            └─ 这个 env_cfg 目前没有被 navigate_to_goal.py 使用
```

`piper_arm.py` 的注释说得很清楚：`"frozen as a decorative payload"`（作为装饰性载荷冻结）。这是早期方案——把 Piper 臂作为**独立的 Articulation** 挂载在 M20 上面（两个独立关节体，不物理连接），现在已被联体方案取代。

### 链路 B：通过 `m20_piper.usda` 的 SubLayer（手工联体版，也已停用）

```
piper/piper_flattened.usd
  └─ 被 m20_piper.usda 通过 subLayers 引用
       └─ m20_piper.usda 被 m20_piper.py 引用
            └─ m20_piper.py 目前无任务使用
```

`m20_piper.usda` 这个手工写的联体 USD 用 `subLayers = [@piper/piper_flattened.usd@]` 把 Piper 臂的几何层叠加进来，是第一代手工联体方案。

**为什么用 `piper_flattened.usd` 而不是 `piper.usd`？** 因为 `piper.usd` 自身还要通过 Reference 去引用 `configuration/` 下的子文件，多层引用在 SubLayer 合成时路径解析容易出错。`piper_flattened.usd` 把所有内容展平到一个文件，SubLayer 引用时路径只有一层，更稳定。

### 总结：piper/ 目录现状

```
piper/
├── piper.usd           → 被 piper_arm.py 引用（但 piper_arm 未被主任务用）
├── piper_flattened.usd → 被 m20_piper.usda 引用（但 m20_piper.py 未被主任务用）  
└── configuration/      → 被 piper.usd 引用（间接废弃）
```

**实际结论**：`piper/` 目录下的所有文件目前对主任务（`navigate_to_goal.py` + `single_piper_env_cfg.py`）**没有任何影响**，它们是早期两代方案的遗留产物。当前主任务完全使用 `m20_piper_single/M20_Piper.usd`（从联体 URDF 自动转换而来），Piper 臂已经是 M20 关节体的一部分，不再是独立 Articulation。
